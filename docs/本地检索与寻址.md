# 本地检索与寻址（非向量）

本文说明 **客服问答** 如何在 **不用向量库** 的前提下，从 SQLite 知识图谱里召回条款，并 **按节号钉住依据**。实现入口：

| 模块 | 路径 |
|------|------|
| 分词与打分 | `src/amendaq/knowledge/search.py` |
| 实体搜索 API | `src/amendaq/knowledge/service.py` → `kg_search_entities` |
| search 后补节号 | `src/amendaq/planning/search_grounding.py` |
| Agent 主链 | `src/amendaq/agent/loop.py` |

---

## 1. 设计立场

- **不做 embedding / chunk RAG**；召回依赖 **确定性分词重合 + 加权打分**。
- **题干（title）** 是运营最该打磨的检索面（权重最高）。
- **节号（section）** 是「严谨寻址」的锚：`kg_get_entity_by_section` / Plan 里的 `graph.entity.by_section`。
- search 命中后若只停留在「搜索结果对象」，可能 **没拉全 leaf 正文**；因此有 **search grounding**（见 §5）。

---

## 2. 图谱里三类文本从哪来

每条 FAQ **叶节点** 发布进 `kg_entity` 时（`graph/extract.py` → `outline` 编译结果）：

| 打分字段 | DB / 属性 | 典型内容 | 运营在 UI 能否单独改 |
|----------|-----------|----------|---------------------|
| **title** | `kg_entity.name` | 叶节点 **标题**（多为整句题干） | ✅ 审核页改「标题」 |
| **summary** | `kg_entity.summary` | 入库时多为 **正文前 280 字**（保存 leaf 时自动写入 `wiki_toc_node.summary`） | ❌ leaf 无独立「摘要」框；改 **答** 会连带更新 summary |
| **body** | `properties.body` | 完整 **答** | ✅ 审核页改「答」 |

**章节点** 在编辑页有「章说明（可选）」→ 仅影响该章的 `summary`，与 FAQ 单条检索无直接关系。

发布链路：`wiki_toc_node` 草稿 → **正式发布** → 图库实体与 evidence 更新。未发布则问答仍读旧图。

---

## 3. 分词（`tokenize`）

中文连续片段 **不做整句当一个 token**（否则用户问句与题干略有差异时得分为 0）。

策略（`search.py`）：

1. 抽出连续汉字段；
2. 若汉字段长度 ≤ 6：**整段为一个 token**（超短标题保底）；
3. 若更长：**重叠二字 bigram**（例：「走势图能投屏」→ `走势`、`势图`、`图能`、`能投`、`投屏`…）；
4. 另外保留英文数字 token（≥2 字符）、金额数字串等。

Plan 里构造搜索关键词时（`planning/query_intent.py`）复用同一套 `tokenize`，与 `kg_search` 一致。

---

## 4. 打分规则（`score_entity`）

对 **用户问句** 的每个 query token \(t\)，在实体三列分词集合里查找，**命中则加分、可叠加**：

| 字段 | 参与分词的范围 | 每个命中 token 加分 |
|------|----------------|---------------------|
| **title** | 全部题干 | **+4** |
| **summary** | 全部 summary 文本 | **+2** |
| **body** | 正文 **前 500 字** | **+1** |

### 4.1 与「title 4、前 280 得 2、前 500 得 1」的对应关系

FAQ leaf 默认 **summary = 正文前 280 字**，因此可记成：

- **title：4**
- **正文前 280 字（summary 列）：2**
- **正文前 500 字（body 列）：1**

注意：

1. **不是**把 body 切成「280 后只剩 1」两段；body 列对 **0～500 字整段** 分词。
2. **0～280 字** 若同时在 summary 与 body 中出现，同一 token 可 **2 + 1 = 3**（题干再有则再加 4）。
3. **281～500 字** 的 token 通常只 **+1**（除非运营手改过 summary，与正文开头不一致）。

### 4.2 降权与兜底

| 条件 | 效果 |
|------|------|
| summary+body 前 400 字含 `Q：` 或「常见问题」 | 总分 **×0.15**（压低附录噪声条） |
| `len(summary) > 600` | 总分 **×0.5** |
| 主循环后得分仍 ≤0 | **子串兜底**：在 `name + summary + body[:400]` 拼接串里若含任一 query token，给 **固定 2 分** 再参与排序 |

`kg_search_entities` 对当前 `document_id` 下候选 `Policy` 实体全表扫描打分，取 Top-N（默认 5），结果中带 `search_score`。

## 5. 严谨寻址：search 之后补 `by_section`

仅 `graph.entity.search` 可能只得到 **轻量 hit**（节号 + 分数），Verify / Compose 需要 **按节拉实体全文**。

`supplement_requirements_after_search`（`search_grounding.py`）在 Agent **一轮 tool 返回后**：

1. 从 `graph_catalog.hits`（或已有 `graph_entities`）取 **score > 0** 的节号，最多 3 个；
2. 向 Plan 补 **`graph.entity.by_section`**（`ensure_by_section_requirements`）；
3. 将新补的 requirement 标为 **未满足**，迫使下一轮真正调用 `kg_get_entity_by_section`。

这样 search 负责 **「找哪一条」**，by_section 负责 **「钉死条款正文」**。

TOC 下钻 / 分批选章（`toc_drill`、`toc_catalog_batch`）与上述 **并行存在**：章级意图弱或 drill 未进第 9 章时，search + grounding 仍可把 §9.2 等条目拉回来（好势 FAQ「投屏」类问题即此类）。

---

## 6. 与 Verify 的关系

Verifier 检查是否 **检索到知识**、回答是否 **引用节号**（有知识时 `answer_cites_section` 可适度放宽）。本地搜索分数进入 trace / eval 时字段名常为 `search_relevance`（`top_score`）。

端到端验收脚本：`scripts/run_haoshi_faq_eval.py` → `data/eval/haoshi_faq_10q.json`。

---

## 7. Wiki 严谨性（与检索分开但相关）

检索再准也依赖 **目录与正文质量**。运营侧另有：

```bash
uv run amendaq wiki audit --doc-id <id>       # 确定性 + 可选 LLM
uv run amendaq wiki audit --doc-id <id> --no-llm
```

报告默认：`data/audit/<doc_id>_rigor.json`；`block_count > 0` 表示须先改 Wiki 再发布。详见 `src/amendaq/wiki/rigor_audit.py`。

---

## 8. 日后改权重或策略时

1. 改 **`score_entity` 三档系数** 或 body 截断长度（现 500）→ 同步更新本文 §4 与单测 `tests/test_knowledge_search.py`。
2. 若产品上要 **运营维护独立「检索摘要」**，需：UI 字段 + 保存时 **禁止** leaf 仅用 body 覆盖 summary + 发布同步图库；当前 **未实现**。
3. 分词策略变更影响所有历史文档的召回分布，应用 eval 集回归。
